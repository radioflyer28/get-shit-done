**`<execution_flow>` block with 7 named steps:**

**Step 1 — `read_skill_files`:**
Read skill_md_path using the Read tool. Store as SKILL_MD_CONTENT.
If workflow_path is non-empty and does NOT start with "UNRESOLVABLE:":
  Read workflow_path using the Read tool. Store as WORKFLOW_CONTENT.
  Set WORKFLOW_LOADED=true.
If workflow_path is empty:
  Set WORKFLOW_LOADED=false.
  WORKFLOW_FAIL = "No <execution_context> @-reference found in SKILL.md"
If workflow_path starts with "UNRESOLVABLE:":
  Set WORKFLOW_LOADED=false.
  WORKFLOW_FAIL = "Workflow file not found: " + workflow_path (strip the "UNRESOLVABLE:" prefix)

**Step 2 — `structural_checks` (AUDIT-02):**
Run each check and record {check_name, result: PASS|FAIL, detail} for each:

1. `frontmatter_keys` — SKILL.md frontmatter contains all three required fields: `name`, `description`,
   `allowed-tools`. FAIL if any are absent. FAIL if `tools:` is present instead of `allowed-tools:`
   (wrong field name for command/skill files). Note: agents use `tools:`, skills use `allowed-tools:`.

2. `objective_present` — SKILL.md contains an `<objective>` block. FAIL if absent.

3. `process_present` — SKILL.md contains a `<process>` block. FAIL if absent.

4. `execution_context_resolves` — Result based on workflow_path from workflow:
   PASS if WORKFLOW_LOADED=true. FAIL with WORKFLOW_FAIL message if false.

5. `step_uniqueness` — (Only if WORKFLOW_LOADED=true) Scan WORKFLOW_CONTENT for all
   `<step name="...">` attributes. FAIL if any name appears more than once. List the duplicates.

6. `task_agent_resolution` — (Only if WORKFLOW_LOADED=true) Find all `Task(` calls in
   WORKFLOW_CONTENT that have `subagent_type="gsd-{x}"`. For each, check if
   `$HOME/.copilot/agents/gsd-{x}.md` OR `$HOME/.claude/agents/gsd-{x}.md` exists using Bash.
   FAIL if any agent file is not found. List missing agents.

7. `required_reading_paths` — For each `@path` in any `<required_reading>` block in SKILL.md
   or WORKFLOW_CONTENT, resolve the path (replace `~` with `$HOME`) and check it exists using Bash.
   FAIL if any path does not exist. List missing paths.

8. `no_hardcoded_claude_paths` — Scan both files for the literal string `~/.claude/` (not
   preceded by `#` — skip commented lines). FAIL if found. Anti-pattern: path must be
   `~/.copilot/` or use a variable. List occurrences.

9. `no_heredoc_patterns` — Scan both files for `cat << 'EOF'` or `cat <<EOF` patterns
   (case-insensitive, not on comment lines). FAIL if found.

Record all results. Count FAIL results as structural_fail_count.

**Step 3 — `smart_scoring` (AUDIT-03):**
For each of the 5 SMART dimensions (S, M, A, R, T) from skill-smart-criteria.md:
- Read the dimension's sub-criteria from skill-smart-criteria.md (already loaded in required_reading)
- Evaluate SKILL.md and WORKFLOW_CONTENT against each sub-criterion
- Assign a score 1–5 using the rubric's scale definitions
- Quote the specific excerpt from SKILL.md or WORKFLOW_CONTENT that is the primary evidence
  for the score (if scoring low, quote what is ABSENT or vague; if scoring high, quote what is PRESENT)
- Write: {dimension_letter, dimension_name, score, evidence_quote, finding_text}

Compute smart_avg = sum of 5 scores / 5 (one decimal place).
Identify smart_worst = minimum score across all 5 dimensions.

**Step 4 — `prompt_quality` (AUDIT-04):**
Evaluate SKILL.md and WORKFLOW_CONTENT against these 6 criteria. For each finding, record
{criterion, severity: HIGH|MEDIUM|LOW, description, affected_section, suggested_fix}:

1. **Clarity** — Are instructions unambiguous? Are verbs concrete (not "handle", "manage", "deal with")?
   HIGH if >2 steps use open-ended verbs in the workflow. MEDIUM if 1–2. LOW if minor wording only.

2. **Context sufficiency** — Does the skill provide enough context for an agent to execute
   without needing to consult external docs or make guesses? HIGH if key inputs/configs are
   unexplained. MEDIUM if some context is implied. No finding if context is complete.

3. **Guardrails** — Does the skill specify error conditions, edge cases, or what NOT to do?
   HIGH if no error handling described anywhere. MEDIUM if partial (only happy path).
   No finding if error paths are explicitly described.

4. **Output format** — Is the completion marker or output format explicitly defined?
   HIGH if no completion signal defined. MEDIUM if defined vaguely ("return results").
   No finding if an explicit completion marker (e.g., `## DONE`) or output file is named.

5. **Error handling** — Are failure paths described with specific error messages?
   HIGH if failures silently pass. MEDIUM if failures mentioned but no message format.
   No finding if failure paths have explicit messages.

6. **GSD anti-patterns** (check all 3 — from skill-authoring.md):
   - Heredoc file writes (`cat << 'EOF'` used to create files) — HIGH severity
   - Overly long steps (any single `<step>` block with >200 words) — MEDIUM severity
   - Mixed decision + execution (a single step both asks user a question AND writes a file) — HIGH severity

Record all findings with severity. Count HIGH-severity findings as high_prompt_count.

**Step 5 — `tool_usage` (AUDIT-05):**
Evaluate WORKFLOW_CONTENT (skip if WORKFLOW_LOADED=false — record all as SKIP) against 6 patterns.
For each finding, record {pattern, severity: HIGH|MEDIUM|LOW, description, file_ref, suggested_fix}:

1. **Task() completeness** — Every `Task(` call has: `subagent_type=` (not just a prompt string),
   `description=`, and the prompt contains concrete context (not just "do the task").
   HIGH if subagent_type missing. MEDIUM if description missing. LOW if prompt is thin.

2. **AskUserQuestion gates** — User-blocking questions are used only for genuine decisions
   that require human judgment. MEDIUM if AskUserQuestion used for something Claude can determine.

3. **Bash() safety** — No `rm -rf {variable}` without prior path validation, no `git push --force`,
   no `git reset --hard` without user confirmation. HIGH severity for each unsafe pattern found.

4. **File operations** — Files are created/modified via Write/Edit tools, not via
   `echo "..." > file` or `tee` in Bash. MEDIUM if Bash is used for file creation.

5. **State management** — If the workflow updates .planning/ files, it uses gsd-tools commands
   rather than direct Write to planning artifacts. LOW if gsd-tools not used for planning state.

6. **Hook integration** — If the workflow description mentions triggering side effects (e.g.,
   running tests after file writes), hooks are mentioned or the workflow calls the relevant
   tool. LOW if missing hook that should logically exist.

**Step 6 — `compute_verdict`:**
Apply D-03 verdict thresholds:

FAIL if ANY of:
- structural_fail_count > 0
- smart_worst < 2

PASS WITH WARNINGS if (no FAIL) AND ANY of:
- smart_avg < 3.5
- high_prompt_count > 0

PASS if:
- No FAIL condition
- smart_avg >= 3.5
- high_prompt_count == 0

Set VERDICT to one of: "PASS", "PASS WITH WARNINGS", "FAIL"
